Question 141 – Topic 1 (Verbatim)

Question:
A company runs production workloads in multiple AWS accounts and AWS Regions. The workloads use Amazon EBS volumes, Amazon RDS databases, and Amazon EFS file systems.
The company must design a solution to meet the following requirements:

Centralized backup management across accounts

Cross-Region disaster recovery

Minimal operational overhead

Automated backup schedules and retention policies

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: B
🧠 Trainer-Level Explanation

This is a governance + DR + managed services question. AWS is testing whether you recognize the one service designed to back up multiple AWS services centrally.

🔑 Step 1: Identify the most important requirement

The phrase that matters most is:

"Centralized backup management across accounts"

This immediately rules out:
• Per-account tooling
• Service-by-service backup logic
• Custom snapshot scripts

🧠 EXAM GOLD:
If backups must be centralized → AWS Backup.

🔑 Step 2: Understand what AWS Backup actually does

AWS Backup:

Centralizes backups for:
• EBS
• RDS
• EFS
• DynamoDB
• FSx

Works across:
• Multiple accounts
• Multiple Regions

Supports:
• Backup plans
• Lifecycle policies
• Cross-Region copy

Integrates with:
• AWS Organizations

This is exactly the problem statement.

🔑 Step 3: Why cross-Region copy matters

AWS Backup supports:
• Automatic copy of recovery points to another Region
• Managed retention in both Regions
• No custom scripts

This satisfies:
• "Cross-Region disaster recovery"

✅ Why Option B is Correct (Deep Dive)

Option B gives:

✅ Centralized management
• One backup account
• One set of policies

✅ Multi-service support
• EBS + RDS + EFS in one place

✅ Cross-Region DR
• Native backup copy
• No Lambda
• No snapshot scripts

✅ Minimal operational overhead
• No EC2
• No cron jobs
• No custom code

This is the AWS-recommended enterprise backup solution.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — DLM policies

Why this fails:

DLM:
• Works only for EBS
• Is account-scoped

Does not cover:
• RDS
• EFS

No centralized governance

❌ Option C — Custom Lambda snapshots

Why AWS hates this:
• Reinvents AWS Backup
• High maintenance
• More failure modes
• Violates "minimal operational overhead"

🧠 Exam rule:
If AWS has a managed service, custom automation is wrong.

❌ Option D — Service-specific backups

Why this fails:
• Fragmented management
• Inconsistent retention
• Hard to audit
• No single pane of glass

🧠 Key SAP-C02 Takeaways (Question 141)

• Centralized backup across services → AWS Backup
• AWS Backup integrates with Organizations
• Cross-Region DR is native in AWS Backup
• Avoid per-service or per-account backup logic
• Managed > custom 
Question 142 – Topic 1 (Verbatim)

Question:
A company runs an application on Amazon EC2 instances in multiple Availability Zones. The application generates and reads a large number of small files that must be shared across all instances.
The company must meet the following requirements:

Shared file access across instances

High availability across Availability Zones

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This is a shared storage design question. AWS is testing whether you understand which storage service supports concurrent, low-latency file access across multiple AZs.

🔑 Step 1: Lock onto the strongest requirement

The key phrase is:

"shared across all instances" + "multiple Availability Zones"

This immediately tells us:

❌ Per-instance storage will not work
❌ Single-AZ storage will not work
✅ We need network file storage

🧠 EXAM GOLD:
If multiple EC2 instances need the same files → network file system, not block or object storage.

🔑 Step 2: Evaluate AWS storage services against the requirements

ServiceShared?Multi-AZ?Ops Overhead
S3❌ (not POSIX mount)✅Low
EBS❌❌Medium
EFS✅✅Low
Instance store❌❌Low

Only EFS satisfies all three requirements.

✅ Why Option C is Correct (Deep Dive)

Option C uses Amazon EFS:

✅ Shared file access
• POSIX-compliant
• Multiple EC2 instances can read/write concurrently

✅ Multi-AZ high availability
• Data replicated across AZs
• No single AZ failure

✅ Minimal ops
• Fully managed
• No capacity planning
• No backups to configure manually (can use AWS Backup)

This is the canonical AWS solution for shared files across EC2.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — S3 mounted on EC2

Why this fails:

S3 is:
• Object storage
• Not a file system

Mounting S3:
• Requires third-party tools
• Breaks POSIX semantics

🧠 Exam rule:
S3 ≠ shared file system.

❌ Option B — EBS volumes

Why this fails:

EBS:
• Can be attached to only one EC2 instance (except limited multi-attach cases)
• Is single-AZ
• Does not support sharing across AZs

❌ Option D — Instance store

Why this fails:
• Ephemeral
• Data lost on stop/terminate
• Instance-scoped only

🧠 Key SAP-C02 Takeaways (Question 142)

• Shared files across EC2 → EFS
• EFS is multi-AZ by default
• EBS is block storage, not shared
• S3 is object storage, not POSIX
• Instance store = temporary only 
Question 143 – Topic 1 (Verbatim)

Question:
A company stores sensitive customer data in an Amazon S3 bucket. Due to regulatory requirements, the company must ensure that the data can be accessed only from within a specific country.
The company must meet the following requirements:

No data replication or duplication

Enforce access restrictions, not just monitor them

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This question is testing enforcement vs observation and data access control vs data placement.

AWS wants you to enforce where data can be accessed from — without moving the data.

🔑 Step 1: Identify what is NOT allowed

The question explicitly says:

"No data replication or duplication"

This immediately eliminates:
❌ Cross-Region Replication
❌ Copying data to new buckets

🔑 Step 2: Identify the type of control required

The phrase:

"must ensure" and "enforce access restrictions"

tells us:

❌ Monitoring-only solutions are insufficient
✅ We must block access at request time

🧠 EXAM GOLD:
If the question says ensure / enforce → bucket policy or IAM policy.

🔑 Step 3: How can S3 restrict access by geography?

S3 does not have a native "country" condition key. But S3 does support IP-based access control.

AWS publishes:
• Country-level IP address ranges (via AWS IP ranges or external sources)

Using an S3 bucket policy with IP conditions:
• Requests from allowed IP ranges succeed
• All others are denied

This enforces data sovereignty at access time.

✅ Why Option C is Correct (Deep Dive)

Option C uses:

S3 bucket policy with IP-based restrictions

This provides:

✅ Enforcement
• Requests outside allowed IP ranges are denied

✅ No data movement
• Data stays in the same bucket

✅ Minimal overhead
• One policy
• No replication
• No monitoring pipelines

This is the simplest enforceable solution.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — Cross-Region Replication

Why this fails:
• Duplicates data
• Violates explicit requirement

Immediate elimination.

❌ Option B — CloudTrail monitoring

Why this fails:
• Detects access
• Does NOT prevent access

🧠 Exam rule:
Monitoring ≠ enforcement.

❌ Option D — KMS key restrictions

Why this is wrong:

KMS Region restrictions:
• Control where keys exist
• Do NOT control request source location

Does not prevent access from outside the country

Wrong control plane.

🧠 Key SAP-C02 Takeaways (Question 143)

• Enforce ≠ monitor
• Data sovereignty often = access control, not replication
• S3 supports IP-based bucket policies
• CloudTrail is observability, not enforcement
• KMS does not enforce geographic access

Question 145 – Topic 1 (Verbatim)

Question:
A company exposes a set of REST APIs by using Amazon API Gateway. The APIs are consumed by external clients.
Due to security requirements, the company must ensure that all client connections use TLS version 1.2 or higher.
The solution must have minimal operational overhead.

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This question is about where TLS is negotiated and which AWS service controls it.

AWS is testing whether you understand:
• TLS happens before the request reaches your code
• Enforcement must happen at the edge / entry point, not downstream

🔑 Step 1: Understand where TLS is actually handled

For API Gateway:

TLS is negotiated:
• Between client and API Gateway

NOT:
• In Lambda
• In custom authorizers
• In application code

🧠 EXAM GOLD:
If TLS is required, enforce it at the service boundary, not in code.

🔑 Step 2: Identify the API Gateway feature that controls TLS

API Gateway provides:

Custom domain names

With configurable:
• TLS security policy
• Minimum TLS version (e.g., TLS 1.2)

This is:
• Native
• Centralized
• Zero code
• Zero runtime overhead

✅ Why Option C is Correct (Deep Dive)

Option C says:

Configure the API Gateway custom domain name to enforce TLS 1.2

This gives:

✅ True enforcement
• TLS versions below 1.2 are rejected at handshake

✅ Minimal overhead
• No code
• No WAF rules
• No custom logic

✅ Centralized security
• Applies to all APIs under the domain
• Easy to audit

This is the AWS-recommended approach.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — Lambda-level rejection

Why this fails:
• Lambda is invoked after TLS negotiation
• Insecure connections already reached AWS

Too late.

❌ Option B — Custom authorizer

Why this fails:

Authorizers:
• Validate identity
• Do not control TLS handshake

TLS is already established before authorizer runs

Wrong layer.

❌ Option D — AWS WAF

Why this is not ideal:

WAF can inspect:
• HTTP headers
• Requests

TLS version enforcement:
• Is better handled at the endpoint configuration

WAF adds:
• Cost
• Complexity

🧠 Exam rule:
If the service has a native security control, use it instead of WAF.

🧠 Key SAP-C02 Takeaways (Question 145)

• TLS is enforced at connection time
• API Gateway custom domains control TLS versions
• Lambda and authorizers cannot enforce TLS
• Native controls > WAF for basic requirements
• Minimal overhead = configuration, not code 
Question 146 – Topic 1 (Verbatim)

Question:
A company uses a centralized CI/CD pipeline in one AWS account to deploy applications to multiple target AWS accounts.
The company must meet the following requirements:

Least privilege access for deployments

No long-lived credentials stored in the pipeline

Auditable access to target accounts

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: B
🧠 Trainer-Level Explanation

This is a textbook cross-account deployment security question. AWS is testing whether you understand identity-based access vs credential sharing.

🔑 Step 1: Lock onto the strongest security requirement

The most important phrase is:

"No long-lived credentials"

This immediately eliminates:
❌ IAM users with access keys
❌ Shared static credentials
❌ Secrets stored for access keys

🧠 EXAM GOLD:
If the question says no long-lived credentials → AssumeRole.

🔑 Step 2: Understand AWS's preferred cross-account access pattern

AWS's recommended model is:

CI/CD Account
|
| sts:AssumeRole
↓
Target Account (IAM Role)

Key benefits:
• Temporary credentials
• Least privilege
• Full audit trail in CloudTrail
• Easy revocation

🔑 Step 3: Why this is perfect for CI/CD pipelines

Using cross-account IAM roles:

The pipeline:
• Assumes a role only when needed
• Gets short-lived credentials

Target account:
• Controls exactly what can be deployed
• Can restrict permissions tightly

This is:
• Secure
• Scalable
• Easy to manage across many accounts

✅ Why Option B is Correct (Deep Dive)

Option B says:

Create a cross-account IAM role in each target account and allow the CI/CD account to assume it

This provides:

✅ Least privilege
• Each role grants only deployment permissions

✅ No long-lived credentials
• STS issues temporary credentials

✅ Auditable access
• CloudTrail logs AssumeRole events

✅ Minimal operational overhead
• Standard AWS pattern
• No secrets rotation
• No shared users

This is the AWS reference architecture for multi-account CI/CD.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — IAM users + access keys

Why this fails:
• Long-lived credentials
• High breach risk
• Manual rotation

Violates requirement directly

Immediate elimination.

❌ Option C — Shared service role

Why this is wrong:
• Roles cannot be "shared" across accounts
• Violates least privilege
• Poor audit isolation

❌ Option D — AWS RAM for credentials

Why this fails:

RAM does not share IAM credentials

RAM is for:
• TGW
• Subnets
• License Manager

Not identities

Classic service misuse trap.

🧠 Key SAP-C02 Takeaways (Question 146)

• Cross-account access = IAM roles
• STS AssumeRole = no long-lived credentials
• IAM users ≠ CI/CD best practice
• Least privilege lives in the target account
• RAM does not share identities 
Question 147 – Topic 1 (Verbatim)

Question:
A company is designing an event-driven architecture on AWS. An application publishes events that trigger downstream processing by multiple consumers.
The company must meet the following requirements:

Decouple producers and consumers

Ensure that no events are lost

Handle spikes in event volume gracefully

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This question is about fan-out reliability and decoupling, not raw throughput.

AWS is testing whether you understand:
• The difference between broadcasting and competing consumers
• How to guarantee delivery to multiple independent consumers

🔑 Step 1: Identify the fan-out requirement (MOST IMPORTANT)

The question says:

"multiple consumers"

This is a critical signal.

🧠 EXAM GOLD:
If every consumer must receive every event → you need fan-out, not a single queue.

🔑 Step 2: Understand the roles of SNS, SQS, and Lambda

Quick refresher:

SNS
• Pub/sub
• Fan-out
• Push-based

SQS
• Durable buffer
• Pull-based
• Competing consumers

Lambda
• Compute
• Not a buffer

🔑 Step 3: Why SNS → SQS is the canonical pattern

The AWS-recommended fan-out pattern is:

Producer
↓
SNS Topic
↓ ↓ ↓
SQS Q1 SQS Q2 SQS Q3
↓ ↓ ↓
Lambda Lambda Lambda

This gives:
• Each consumer its own queue
• Independent scaling
• Independent retries
• No event loss

✅ Why Option C is Correct (Deep Dive)

Option C uses:

SNS topic + multiple SQS subscriptions

This provides:

✅ Decoupling
• Producer doesn't know consumers

✅ No event loss
• SQS durably stores messages
• Retries are automatic

✅ Spike handling
• SQS buffers spikes
• Consumers scale independently

✅ Minimal overhead
• Fully managed services
• No shard management
• No custom retry logic

This is textbook AWS event-driven design.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — Direct Lambda invocation

Why this fails:
• Tight coupling
• No buffering
• If a Lambda fails → event lost (unless custom retries)
• Poor spike handling

❌ Option B — Single SQS queue with multiple Lambdas

Why this is wrong:

This is competing consumers
• Each event goes to only one Lambda

Does NOT satisfy "multiple consumers"

🧠 Exam rule:
Multiple Lambdas on one SQS queue = load balancing, not fan-out.

❌ Option D — Kinesis Data Streams

Why this is not ideal:
• Requires shard management
• Higher operational overhead
• More complex scaling
• Overkill unless ordering or stream replay is required

🧠 Exam rule:
If SNS + SQS works, Kinesis is usually too much.

🧠 Key SAP-C02 Takeaways (Question 147)

• Fan-out = SNS
• Durability & buffering = SQS
• SNS → SQS = best-of-both-worlds
• One SQS queue ≠ multiple consumers
• Kinesis only when streaming semantics are required 
Question 148 – Topic 1 (Verbatim)

Question:
A company runs workloads on Amazon EC2 instances in private subnets. The workloads need outbound internet access for software updates and external API calls.
The company must meet the following requirements:

No inbound internet access to the instances

Controlled and auditable outbound internet access

Highly available solution

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: B
🧠 Trainer-Level Explanation

This question is about egress-only internet access for private workloads.

AWS is testing whether you understand:
• The difference between IGW vs NAT
• How to build highly available outbound access
• How to avoid exposing private instances to inbound traffic

🔑 Step 1: Lock onto the "no inbound access" requirement

The question clearly states:

"No inbound internet access"

This immediately eliminates:
❌ Internet Gateway directly attached to private subnets

🧠 EXAM GOLD:
Private subnets never route directly to an Internet Gateway.

🔑 Step 2: Identify AWS's managed egress solution

AWS provides a purpose-built service for this:

NAT Gateway

What NAT Gateway does:
• Allows outbound-only internet access
• Blocks unsolicited inbound connections
• Is fully managed
• Scales automatically

🔑 Step 3: Why high availability matters here

To be highly available:

NAT Gateway must be:
• Deployed in each AZ

Each private subnet routes to:
• The NAT Gateway in the same AZ

This avoids:
• AZ dependency
• Single point of failure
• Cross-AZ traffic charges

✅ Why Option B is Correct (Deep Dive)

Option B says:

Deploy NAT gateways in each Availability Zone

This provides:

✅ Outbound-only internet access
• No inbound exposure

✅ Controlled egress
• All outbound traffic flows through NAT

✅ High availability
• One NAT Gateway per AZ

✅ Minimal ops
• No EC2 to manage
• No scaling configuration

This is the AWS reference architecture for private subnet egress.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — Internet Gateway

Why this is wrong:
• Allows inbound traffic
• Violates private subnet isolation

Immediate elimination.

❌ Option C — EC2-based proxy

Why AWS rejects this:

Requires:
• Patch management
• Scaling
• Monitoring

Higher operational overhead than NAT Gateway

🧠 Exam rule:
If a managed service exists, do not use EC2 unless required.

❌ Option D — VPC peering for egress

Why this fails:

VPC peering:
• Is not transitive
• Not intended for internet egress
• Adds complexity without benefit

🧠 Key SAP-C02 Takeaways (Question 148)

• Private subnet egress = NAT Gateway
• Never route private subnets directly to IGW
• One NAT Gateway per AZ for HA
• Proxies add unnecessary ops
• Managed > self-managed

Question 150 – Topic 1 (Verbatim)

Question:
A company stores critical customer data in an Amazon DynamoDB table. The company has experienced incidents where administrators accidentally deleted items from the table.
The company must meet the following requirements:

Prevent accidental data deletion

Minimal operational overhead

Ability to recover deleted data

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: A
🧠 Trainer-Level Explanation

This question is about recoverability, not access restriction, and not event tracking.

AWS is testing whether you know the simplest native feature that protects against human error.

🔑 Step 1: Understand what "prevent accidental deletion" REALLY means

The requirement says:

"Prevent accidental data deletion"

In AWS exam language, this often means:
• You can't realistically stop every delete
• But you must be able to undo accidental deletes quickly

This is logical prevention, not strict enforcement.

🧠 EXAM GOLD:
If the question mentions accidental deletion → think recovery, not hard denies.

🔑 Step 2: Identify DynamoDB's native safety feature

DynamoDB provides:

Point-in-Time Recovery (PITR)

PITR:
• Continuous backups
• Second-by-second recovery
• Up to 35 days
• No performance impact
• No code changes

This is exactly designed for this scenario.

🔑 Step 3: Why PITR beats other approaches

Compared to alternatives:
• No Lambda
• No S3
• No IAM gymnastics
• No restore scripting

PITR is:
• One checkbox
• Fully managed
• Very low cost
• Highly reliable

✅ Why Option A is Correct (Deep Dive)

Option A enables:

✅ Protection from accidental deletes
• Restore table to any second in last 35 days

✅ Minimal ops
• No workflows
• No automation
• No monitoring

✅ Fast recovery
• Restore entire table or to a new table

This is the AWS-recommended solution.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option B — AWS Backup

Why this is inferior:

Backup frequency is:
• Periodic
• Not continuous

Higher RPO

More configuration than PITR

PITR is purpose-built for DynamoDB.

❌ Option C — Streams + Lambda

Why AWS rejects this:
• Custom logic
• Missed edge cases
• Higher failure risk
• More operational overhead

🧠 Exam rule:
If DynamoDB has a native feature, do not reinvent it.

❌ Option D — Deny DeleteItem

Why this fails:
• Legitimate deletes may be required
• Breaks application behavior
• Does not solve recovery if a privileged user deletes data

🧠 Key SAP-C02 Takeaways (Question 150)

• Accidental deletion → recovery, not denial
• DynamoDB PITR = built-in safety net
• PITR has minimal overhead
• IAM denies are too blunt
• Native features > custom solutions
