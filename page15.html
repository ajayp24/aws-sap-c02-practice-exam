Question 131 – Topic 1 (Verbatim)

Question:
A company runs development and test environments on Amazon EC2 instances in multiple AWS accounts. These environments are used only during business hours (8 a.m. to 6 p.m., Monday through Friday).
The company wants to reduce costs by ensuring that the EC2 instances are automatically stopped outside business hours and started again before the next business day.
The solution must meet the following requirements:

Minimal operational overhead

Centralized management across accounts

No changes to existing applications

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: B
🧠 Trainer-Level Explanation

This is a predictable-schedule cost optimization problem. AWS is testing whether you can recognize:

• Predictable usage patterns
• Native scheduling capabilities
• Event-driven automation

🔑 Step 1: Identify the usage pattern

Key phrase:

"only during business hours"

This tells us:

• The schedule is known and predictable
• No machine learning
• No manual review required

🧠 EXAM RULE:
If usage follows a predictable schedule → schedule-based automation.

🔑 Step 2: Identify the control mechanism AWS prefers

AWS has a very clean, serverless pattern for this:

EventBridge (cron)
↓
Lambda
↓
EC2 Stop/Start (tag-based)

Why this is preferred:

• Fully serverless
• No servers to manage
• Easy to extend across accounts
• Tag-driven (safe and selective)

🔑 Step 3: Why tagging matters (important nuance)

Using tags:

• Prevents stopping production instances
• Allows per-team control
• Enables centralized governance

This matches:

"centralized management across accounts"

✅ Why Option B is Correct (Deep Dive)

Option B gives:

✅ Minimal operational overhead
• No EC2
• No cron servers
• No manual execution

✅ Centralized control
• One Lambda per account or centralized via cross-account roles
• Consistent behavior everywhere

✅ No app changes
• Stop/start is infrastructure-only

This is the canonical AWS solution for scheduled EC2 cost optimization.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — Cost Explorer + Budgets

Why this fails:

Budgets:
• Alert only
• Do not take action
• Manual intervention required

🧠 Exam rule:
If the question says "automatically", alert-only solutions are wrong.

❌ Option C — SSM Automation (manual)

Why this is inferior:

Automation documents are useful

But:
• Manual execution adds overhead
• Scheduling still required elsewhere

AWS prefers EventBridge-native scheduling.

❌ Option D — Auto Scaling scheduled actions

Why this is risky:

Works only for:
• Auto Scaling groups

May:
• Terminate instances
• Lose state

Not all dev/test workloads use ASGs

🧠 Exam rule:
If instances must be restarted intact → stop/start, not scale-to-zero.

🧠 Key SAP-C02 Takeaways (Question 131)

• Predictable schedules → EventBridge cron
• Automation → Lambda
• Tag-based control prevents accidents
• Budgets ≠ automation
• Stop/start ≠ scale-to-zero 
Question 132 – Topic 1 (Verbatim)

Question:
A company has hundreds of AWS accounts that are managed by using AWS Organizations with all features enabled. The company wants to ensure that all Amazon EBS volumes are encrypted at rest for current and future EC2 instances.
The solution must meet the following requirements:

Enforce encryption (not just detect it)

Apply automatically to existing and new accounts

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This question is all about the difference between:

• Detection
• Correction
• Prevention

AWS is explicitly asking for enforcement, not alerts and not cleanup.

🔑 Step 1: Identify the strongest keyword

The most important word in the question is:

"ensure" and "enforce encryption"

This immediately tells us:

❌ Detection-only solutions are insufficient
❌ Post-creation remediation is insufficient
✅ The resource must be blocked at creation time if noncompliant

🧠 EXAM RULE:
If the question says ensure / enforce / prevent → SCP or IAM, not Config.

🔑 Step 2: Understand how EBS encryption works in AWS

Important facts:

• EBS encryption is set at volume creation
• You cannot encrypt an existing unencrypted volume in place

EBS encryption by default:
• Helps
• But is account-scoped
• Can be turned off by admins

🔑 Step 3: Why SCP is the correct tool

Service Control Policies (SCPs):

Apply to:
• All accounts in OUs
• Including future accounts

• Cannot be bypassed
• Are evaluated before IAM permissions

An SCP that denies:

• ec2:CreateVolume
• ec2:RunInstances

without encryption parameters

→ guarantees encryption always

✅ Why Option C is Correct (Deep Dive)

Option C says:

Create an SCP that denies the creation of unencrypted EBS volumes

This gives:

✅ True enforcement
• Unencrypted volumes cannot be created
• Period

✅ Automatic coverage
• Existing accounts
• New accounts added later

✅ Minimal ops
• No Lambda
• No monitoring
• No remediation jobs

This is enterprise-grade preventive security.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — Encryption by default + Config

Why this is insufficient:

Encryption by default:
• Is per-account
• Can be disabled

Config:
• Detects after creation
• Violates "enforce"

🧠 Exam rule:
Defaults help, but they are not enforcement.

❌ Option B — Config + Lambda remediation

Why AWS dislikes this:

• Volume is created unencrypted first
• Data may already be written

Requires:
• Snapshots
• New volumes
• High operational overhead

Detection + fix ≠ prevention.

❌ Option D — Security Hub

Why this fails:

Security Hub:
• Aggregates findings
• Does not block actions
• No enforcement capability

Wrong service category.

🧠 Key SAP-C02 Takeaways (Question 132)

• Encryption must be enforced at creation time
• Prevention > detection > remediation
• SCPs are the strongest governance tool
• Defaults are not guarantees
• Security Hub ≠ enforcement 
Question 133 – Topic 1 (Verbatim)

Question:
A company runs a serverless application in a single AWS Region. The application accesses external URLs and extracts metadata from those sites.
The company uses an Amazon Simple Notification Service (Amazon SNS) topic to publish URLs to an Amazon Simple Queue Service (Amazon SQS) queue. An AWS Lambda function uses the queue as an event source and processes the URLs from the queue. Results are saved to an Amazon S3 bucket.

The company wants to process each URL in other AWS Regions to compare possible differences in site localization.

URLs must be published from the existing Region.

Results must be written to the existing S3 bucket in the current Region.

Which combination of changes will produce a multi-Region deployment that meets these requirements? (Choose two.)

Options (Verbatim)
✅ Correct Answers: A and C
🧠 Trainer-Level Explanation

This question is a pure fan-out architecture problem. AWS wants to see if you understand who publishes, who subscribes, and how cross-Region messaging works.

🔑 Step 1: Identify the invariant (what must NOT change)

The question clearly states:

"URLs must be published from the existing Region."

That means:

❌ We cannot move or replicate the SNS topic
❌ We cannot change the publisher logic
✅ SNS remains centralized

🧠 EXAM RULE:
If the publisher must remain in one Region → fan-out must happen downstream.

🔑 Step 2: Understand SNS vs SQS roles

Important fundamentals (MEMORIZE):

• SNS = publisher / fan-out
• SQS = consumer buffer

SNS can publish to:
• SQS
• Lambda
• HTTP/S

• SNS supports cross-Region delivery
• SQS does not fan-out by itself

🔑 Step 3: Correct multi-Region fan-out pattern

The AWS-approved pattern looks like this:

Region A (publisher)
SNS Topic
↓
SQS (Region A) → Lambda (Region A)
SQS (Region B) → Lambda (Region B)
SQS (Region C) → Lambda (Region C)

Each Region:
• Processes the same message
• Writes results back to the same S3 bucket

✅ Why Option A is Correct

A. Deploy the SQS queue with the Lambda function to other Regions

Why this is required:

Each Region needs:
• Its own queue
• Its own Lambda

Enables:
• Parallel processing
• Region-specific execution
• Keeps compute local to each Region

Without this, there is nowhere for regional processing to happen.

✅ Why Option C is Correct

C. Subscribe the SQS queue in each Region to the SNS topic

This is the fan-out mechanism.

• SNS publishes once
• Each regional SQS queue receives a copy
• Cross-Region delivery is handled natively by SNS

🧠 EXAM GOLD:
Multi-Region fan-out = SNS → multiple SQS queues (cross-Region).

❌ Why the Other Options Are WRONG (Classic Exam Traps)

❌ Option B — Subscribe SNS topics in each Region

Why this fails:

• SNS topics would need to be created in each Region

Violates:
• "URLs must be published from the existing Region"

Wrong direction of subscription.

❌ Option D — SQS publishing to SNS

Why this is incorrect:

• SQS does not publish messages
• SQS is a pull-based queue
• This reverses the correct SNS/SQS relationship

🧠 Exam rule:
SNS publishes, SQS subscribes — never the other way around.

🧠 Key SAP-C02 Takeaways (Question 133)

• SNS = fan-out, SQS = buffer
• SNS supports cross-Region delivery
• Multi-Region processing = regional consumers
• Publisher stays centralized
• SQS never publishes to SNS 
Question 134 – Topic 1 (Verbatim)

Question:
A company runs a proprietary stateless ETL application on Amazon EC2 Linux instances. The application is a Linux binary, and the source code cannot be modified. The application is single-threaded, uses 2 GB of RAM, and is highly CPU intensive.
The application is scheduled to run every 4 hours and runs for up to 20 minutes. A solutions architect wants to revise the architecture for the solution.

Which strategy should the solutions architect use?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This is a "pick the right compute for a scheduled job" question. AWS is testing whether you understand runtime limits, scheduling, and operational overhead.

🔑 Step 1: Immediately eliminate Lambda (VERY IMPORTANT)

The application:
• Runs up to 20 minutes

AWS Lambda:
• Max execution time = 15 minutes

🧠 EXAM GOLD:
If runtime > 15 minutes → Lambda is impossible.

So:
❌ Option A is immediately wrong

🔑 Step 2: Understand the workload characteristics

Workload is:
• Stateless
• CPU intensive
• Runs on a schedule
• No code changes allowed

This points to:
• Containers
• Serverless container execution
• No long-lived infrastructure

🔑 Step 3: Why AWS Fargate is preferred here

AWS Fargate:
• Runs containers without managing servers
• Supports CPU-heavy workloads
• Supports long-running tasks
• Integrates natively with EventBridge scheduling

This fits perfectly.

✅ Why Option C is Correct (Deep Dive)

Option C says:

Use AWS Fargate + EventBridge scheduling

This gives:

✅ No code changes
• Package binary in a container

✅ Serverless execution
• No EC2 management
• No patching
• No capacity planning

✅ Native scheduling
• EventBridge cron rules
• Reliable execution

✅ Scales cleanly
• Each run is isolated
• No leftover instances

This is the canonical AWS solution for scheduled container jobs.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option B — AWS Batch

Why this is tempting:
• Batch workloads
• CPU intensive

Why AWS rejects it here:

AWS Batch:
• Is more complex
• Requires compute environments
• Adds operational overhead

The question asks for least complexity

🧠 Exam rule:
If Fargate works, AWS Batch is usually overkill.

❌ Option D — Spot Instances + CodeDeploy

Why this fails:

Spot instances:
• Can be interrupted
• Not guaranteed to run every 4 hours

CodeDeploy:
• Not a scheduler
• High operational burden

🧠 Key SAP-C02 Takeaways (Question 134)

• Lambda max runtime = 15 minutes
• Scheduled jobs > 15 min → containers
• Fargate = serverless containers
• EventBridge = scheduling
• Batch = only when Fargate is insufficient 
Question 135 – Topic 1 (Verbatim)

Question:
A company has a central shared services VPC that hosts internal APIs. The APIs are exposed by using Network Load Balancers (NLBs) in the shared services account.
Multiple application teams run workloads in separate AWS accounts and VPCs. The application teams need to privately access the internal APIs.
The company must meet the following requirements:

Traffic must not traverse the public internet

Overlapping CIDR ranges exist between some VPCs

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: B
🧠 Trainer-Level Explanation

This question is a classic PrivateLink vs Transit Gateway vs Peering decision problem.

AWS is testing whether you recognize the three key signals that immediately eliminate other options.

🔑 Step 1: Lock onto the CIDR overlap requirement

The question explicitly says:

"Overlapping CIDR ranges exist between some VPCs"

This is a hard constraint.

🧠 EXAM GOLD:
If CIDRs overlap → VPC peering and Transit Gateway are invalid.

Why?
• Both require unique, non-overlapping CIDRs
• Routing becomes impossible otherwise

So:
❌ Option A (VPC peering) is out
❌ Option C (Transit Gateway) is out

🔑 Step 2: Lock onto the "no public internet" requirement

Traffic must:
• Stay private
• Use AWS backbone
• Not require NAT or IGW

This eliminates:
❌ VPNs (they traverse public internet, even if encrypted)

🔑 Step 3: Identify the AWS service designed for THIS exact use case

Remaining option:

AWS PrivateLink

What PrivateLink gives you:
• Private connectivity
• No CIDR overlap issues
• No route table complexity
• NLB-based service exposure
• Scales to many VPCs/accounts

🧠 EXAM RULE:
PrivateLink ignores CIDR overlap entirely.

✅ Why Option B is Correct (Deep Dive)

Option B uses:
• PrivateLink endpoint service (provider side)
• Interface VPC endpoints (consumer side)

This provides:

✅ Private connectivity
• Traffic stays on AWS network
• No IGW
• No NAT

✅ CIDR overlap support
• No routing required
• No IP visibility between VPCs

✅ Minimal operational overhead
• No route table management
• No mesh networking
• Simple permissions-based access

This is the canonical AWS shared services pattern.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option A — VPC peering

Why this fails:
• Requires non-overlapping CIDRs
• Requires route table management
• Becomes unmanageable at scale

❌ Option C — Transit Gateway

Why this fails:
• Does not support overlapping CIDRs
• Overkill for simple service exposure
• Higher cost and complexity

❌ Option D — Site-to-Site VPN

Why this fails:
• Traverses public internet
• High operational overhead
• Poor scalability
• Latency

🧠 Exam rule:
VPN is almost never the answer for intra-AWS connectivity.

🧠 Key SAP-C02 Takeaways (Question 135)

• Overlapping CIDRs = PrivateLink
• PrivateLink works with NLB
• No routing required with PrivateLink
• Transit Gateway ≠ overlapping CIDRs
• VPN ≠ private AWS-only traffic

• Passive traffic analysis

The phrase that decides everything is:

"No impact on application performance"

❌ We cannot put anything inline

If traffic must be analyzed without affecting performance → mirror it, don't route it.

FeatureGateway Load BalancerTraffic Mirroring

Passive copy❌ No✅ Yes

Use caseFirewall / IPSMonitoring / analysis

VPC Traffic Mirroring:
• Copies ENI traffic
• Sends a copy to:
- EC2
- NLB
- Third-party appliances
• Works in near real time
• Does not modify or delay traffic

✅ Why Option B is Correct (Deep Dive)

Use VPC Traffic Mirroring

Question:

The resource is:

Amazon ECR repository

Key AWS fact (EXAM GOLD):

ECR supports resource-based policies

That means:
• The resource itself (ECR repo) can grant access

• No credentials need to be passed around

🔑 Step 2: Match requirements to the simplest AWS-native mechanism

Requirements:

❌ No duplication → replication is out
❌ Least operational overhead → avoid role choreography
✅ Secure, cross-account access

This points directly to:

ECR repository policies

Create an ECR repository policy that allows the application accounts to pull images

✅ No image duplication
• Single source of truth
• Central image lifecycle management

✅ Least operational overhead
• One policy on the repository
• No roles to create per account
• No trust relationships to maintain

✅ Secure access

Fine-grained permissions:
• ecr:GetDownloadUrlForLayer

Account-level or role-level principals

This is the AWS-recommended pattern for ECR sharing.

❌ Option A — Cross-account role assumption

Why this is inferior:

Works technically

But:

Why this is bad design:
• Image duplication
• Sync complexity

• Violates "least operational overhead"

🧠 Key SAP-C02 Takeaways (Question 138)

Question 140 – Topic 1 (Verbatim)

Question:
A company has an application that uses AWS Lambda to process requests. The Lambda function must connect to an Amazon RDS MySQL database that runs in a private subnet in a VPC.
The company has the following requirements:

No database credentials can be stored in the Lambda function code or environment variables

Access must be secure and auditable

Minimal operational overhead

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: B
🧠 Trainer-Level Explanation

This is a secure-access design question, not a secrets-storage question. AWS is testing whether you understand when to eliminate credentials entirely instead of just protecting them.

🔑 Step 1: Lock onto the strongest constraint

The most important requirement is:

"No database credentials can be stored"

This immediately tells us:

❌ Secrets Manager is not ideal
❌ Parameter Store is not ideal
❌ S3 is absolutely wrong

Why?
All three still involve stored credentials

🧠 EXAM GOLD:
If the question says no credentials can be stored → eliminate credentials, don't rotate them.

🔑 Step 2: Identify AWS's credential-less database access feature

AWS provides one clean solution:

IAM Database Authentication

What this does:
• Uses temporary IAM credentials
• No usernames/passwords stored
• Tokens are short-lived
• Fully auditable via CloudTrail

This is exactly what the requirement describes.

🔑 Step 3: Why IAM DB Auth works perfectly with Lambda

Lambda already:
• Has an execution role
• Uses temporary credentials
• Integrates natively with IAM

With IAM DB auth:
• Lambda generates a token
• Token is valid for minutes
• Database verifies IAM role

No secrets, no rotation, no storage.

✅ Why Option B is Correct (Deep Dive)

Option B says:

Enable IAM database authentication and grant the Lambda execution role permission

This gives:

✅ No stored credentials
• No secrets anywhere

✅ Secure & auditable
• IAM policies
• CloudTrail logs

✅ Minimal operational overhead
• No rotation logic
• No secret lifecycle management
• No application changes beyond auth config

This is AWS's preferred best practice when supported.

❌ Why the Other Options Are WRONG (Classic Exam Traps)

❌ Option A — Secrets Manager

Why this looks good:
• Secure
• Rotatable
• AWS-managed

Why it fails:
• Credentials are still stored
• Violates explicit requirement

🧠 Exam rule:
If IAM auth is available, AWS prefers it over Secrets Manager.

❌ Option C — Parameter Store

Why this is worse:
• Manual rotation (or custom)
• Credentials still stored
• More operational overhead than Secrets Manager

❌ Option D — Encrypted S3

Why this is completely wrong:
• Static secrets
• No rotation
• Poor access control model

Immediate elimination.

🧠 Key SAP-C02 Takeaways (Question 140)

• Eliminate credentials whenever possible
• IAM DB Authentication > Secrets Manager (when supported)
• Lambda integrates naturally with IAM auth
• Stored secrets = higher risk + overhead
• "Secure" ≠ "credential-less"
