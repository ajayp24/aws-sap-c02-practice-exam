AWS Solution Architect – Practice Test (Page 13)

Question 111 – Topic 1 (Verbatim)

Question:
A solutions architect is auditing the security setup of an AWS Lambda function for a company. The Lambda function retrieves the latest changes from an Amazon Aurora database. The Lambda function and the database run in the same VPC.
Lambda environment variables are providing the database credentials to the Lambda function.
The Lambda function aggregates data and makes the data available in an Amazon S3 bucket that is configured for server-side encryption with AWS KMS managed encryption keys (SSE-KMS).
The data must not travel across the Internet. If any database credentials become compromised, the company needs a solution that minimizes the impact of the compromise.

What should the solutions architect recommend to meet these requirements?

Options (Verbatim)
✅ Correct Answer: A
🧠 Trainer-Level Explanation

This is a security + networking combo question, and it’s packed with exam signals.

🔑 Step 1: Identify the TWO hard requirements (do not mix them up)

There are two separate constraints:

1️⃣ “The data must not travel across the Internet”

This is a networking requirement, not an encryption requirement.

2️⃣ “Minimize the impact if database credentials are compromised”

This is an authentication / credential model requirement.

AWS expects you to solve both, not just one.

🔑 Step 2: Understand why the CURRENT design is bad

Current state:

Lambda uses environment variables for DB credentials

Problems:

Credentials are long-lived
If leaked → attacker has full DB access
Rotation is manual or brittle

🧠 Exam rule:
Environment variables with static credentials = ❌ for security-sensitive systems.

🔑 Step 3: How do we eliminate database credentials entirely?

AWS has one clean answer:

IAM database authentication

What this does:

No username/password stored
Lambda uses its IAM role
Short-lived auth tokens

If compromised → token expires quickly

This directly satisfies:

“minimize the impact of credential compromise”

🔑 Step 4: Handle the “must not travel across the Internet” requirement

This is where many people get tricked.

Important fact:

HTTPS does NOT mean “not using the Internet”

HTTPS still traverses the public AWS endpoint unless a VPC endpoint exists

To keep S3 traffic inside AWS’s private network, you need:

A gateway VPC endpoint for Amazon S3

This ensures:

No Internet Gateway
No NAT Gateway
Traffic stays on AWS backbone

✅ Why Option A is Correct (Deep Dive)

Option A does both required things, cleanly and minimally:

✅ Solves credential compromise

IAM DB authentication
No stored secrets
Short-lived tokens

✅ Solves “no Internet” requirement

Gateway VPC endpoint for S3
Private routing inside AWS

✅ Minimal operational overhead

No secret rotation workflows
No custom credential logic
Uses native AWS integrations

This is textbook AWS Well-Architected security.

❌ Why the Other Options Are WRONG (Important Exam Traps)

❌ Option B — IAM DB auth + HTTPS only

Why this fails

HTTPS ≠ private networking
Traffic still goes over public S3 endpoints
Violates “must not travel across the Internet”

🧠 Exam rule:
If the question says “must not travel across the Internet” → you need a VPC endpoint, not just encryption.

❌ Option C — Parameter Store + rotation

Why this is inferior

Still uses stored credentials
Rotation ≠ elimination of credentials
More operational complexity than IAM DB auth

Parameter Store is good — but not best here.

❌ Option D — Secrets Manager + rotation

Why this looks tempting (but is wrong)

Secrets Manager is excellent
Rotation is great

But:

Still long-lived credentials
Does NOT eliminate credential compromise
HTTPS alone doesn’t prevent Internet traversal

🧠 Exam rule:
If IAM-based auth is available, AWS prefers it over stored secrets.

🧠 Key SAP-C02 Takeaways

IAM DB authentication > Secrets Manager (when available)
HTTPS ≠ private networking
“Must not travel across Internet” = VPC endpoint
Eliminate credentials > rotate credentials
Gateway VPC endpoint is required for S3 private access 
Question 112 – Topic 1 (Verbatim)

Question:
A large mobile gaming company has successfully migrated all of its on-premises infrastructure to the AWS Cloud. A solutions architect is reviewing the environment to ensure that it was built according to the design and that it is running in alignment with the Well-Architected Framework.
While reviewing previous monthly costs in Cost Explorer, the solutions architect notices that the creation and subsequent termination of several large instance types account for a high proportion of the costs. The solutions architect finds out that the company’s developers are launching new Amazon EC2 instances as part of their testing and that the developers are not using the appropriate instance types.
The solutions architect must implement a control mechanism to limit the instance types that only the developers can launch.

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This question is about preventive controls, not monitoring, not best practices, and not documentation.

AWS is testing whether you know how to STOP something from happening, not just detect it.

🔑 Step 1: Understand the real problem

What’s happening?

Developers:

Are launching EC2 instances
Are choosing large instance types

Result:

High cost
Instances launched and terminated repeatedly

Requirement:

Limit what developers can launch

Must be a control mechanism

Key word:

limit

This immediately tells us:

❌ Reporting-only solutions are insufficient

❌ Detection-only solutions are insufficient

✅ Must block the action

🔑 Step 2: Understand what kind of control AWS wants

AWS has three main control types:

Detective (after the fact)
→ AWS Config, logs, reports

Preventive (before it happens)
→ IAM policies, SCPs

Corrective (after detection)
→ Lambda remediation

This question explicitly wants a preventive control.

🔑 Step 3: Identify who is being restricted

The question says:

“limit the instance types that only the developers can launch”

This tells us:

Restriction is role/user-based
Not organization-wide
Not account-wide

So:

SCPs would be too broad
IAM policies are the right tool

✅ Why Option C is Correct (Deep Dive)

Option C says:

Create an IAM policy that specifies allowed instance types and attach it to an IAM group for developers

This is the cleanest preventive control:

IAM supports conditions on ec2:InstanceType

Policy can:

Allow t3.micro, t3.small, etc.

Deny everything else

Applies only to developers

Blocks the launch before it happens

This:

Directly controls cost
Aligns with Well-Architected (Cost Optimization pillar)
Has minimal overhead

🧠 EXAM GOLD:
IAM policies are the only way here to proactively prevent the launch of specific instance types by specific users.

❌ Why the Other Options Are WRONG (Important Traps)

❌ Option A — AWS Config rule

Why this fails

AWS Config:

Detects noncompliance
Does not prevent launches

Even with remediation:

Instance is already launched
Cost is already incurred

🧠 Exam rule:
If the question says limit / prevent, AWS Config alone is wrong.

❌ Option B — Launch templates

Why this fails

Launch templates:

Can restrict instance types

But only when they are used

Developers can:

Ignore templates
Use CLI / SDK
Launch instances directly

This is not enforceable.

❌ Option D — EC2 Image Builder

Why this is irrelevant

Image Builder controls:

AMIs

It does not control:

Instance size
Instance type

Developers could still launch large instances using the AMI

This option addresses a different problem entirely.

🧠 Key SAP-C02 Takeaways

Preventive controls = IAM or SCP
AWS Config = detection, not prevention
Launch templates are optional, not enforceable
IAM policies can restrict ec2:InstanceType
Cost optimization often = permission control

Question:
A company is developing and hosting several projects in the AWS Cloud. The projects are developed across multiple AWS accounts under the same organization in AWS Organizations.
The company requires the cost for cloud infrastructure to be allocated to the owning project. The team responsible for all of the AWS accounts has discovered that several Amazon EC2 instances are lacking the Project tag used for cost allocation.

Which actions should a solutions architect take to resolve the problem and prevent it from happening in the future? (Choose three.)

Options (Verbatim)
✅ Correct Answers: A, B, E
🧠 Trainer-Level Explanation

This question is about governance at scale.
AWS is testing whether you understand how to combine detection + prevention + centralized visibility.

You must do three things:

Find existing problems
Prevent future problems
See everything centrally across accounts

Each selected option must clearly map to one of these goals.

🔑 Step 1: Break the requirement into three buckets

Let’s translate the question into architecture language.

Requirement 1:

“several EC2 instances are lacking the Project tag”

➡ We need detection of missing tags.

Requirement 2:

“prevent it from happening in the future”

➡ We need prevention, not just alerts.

Requirement 3:

“multiple AWS accounts under an organization”

➡ We need centralized, org-wide visibility.

🔑 Step 2: Map AWS services to each requirement

Requirement AWS Capability

Detect missing tags AWS Config

Prevent untagged launches SCP

Centralized view Config Aggregator

Once you see this mapping, the answer becomes very clear.

✅ Why A, B, and E are CORRECT

✅ Option A — AWS Config rule (Detection)

Create an AWS Config rule to find resources with missing tags

Why this is required

AWS Config:

Continuously evaluates resource configuration
Can detect missing or incorrect tags

This addresses existing EC2 instances

🧠 Exam rule:
AWS Config = detect & evaluate, not prevent.

✅ Option B — SCP deny on RunInstances (Prevention)

Deny ec2:RunInstances if Project tag is missing

Why this is critical

SCPs:

Apply across the organization
Cannot be bypassed

Prevents:

Untagged EC2 launches
Cost leakage

Enforces tagging before the instance is created

🧠 EXAM GOLD:
Tag enforcement at creation time = SCP, not IAM alone.

✅ Option E — AWS Config Aggregator (Centralized visibility)

Aggregate compliance results across accounts

Why this is necessary

Company has multiple accounts

Without an aggregator:

You must check each account manually

Aggregator provides:

Single-pane-of-glass view
Organization-wide compliance reporting

🧠 Exam rule:
Multi-account visibility = Config Aggregator.

❌ Why the Other Options Are WRONG (Important Exam Traps)

❌ Option C — Amazon Inspector

Why this is wrong

Inspector is for:

Vulnerabilities
CVEs
Runtime risk

It does not evaluate tags

Wrong tool, wrong problem.

❌ Option D — IAM policy deny in each account

Why this is inferior to SCP

IAM policies:

Are account-specific
Can be overridden

SCPs:

Are organization-wide
Cannot be bypassed

🧠 Exam rule:
Organization-wide enforcement = SCP > IAM.

❌ Option F — AWS Security Hub

Why this is wrong

Security Hub:

Aggregates security findings

Not tagging compliance

Tags are cost governance, not security posture

Another “sounds enterprise” trap.

🧠 Key SAP-C02 Takeaways

Detection = AWS Config
Prevention = SCP
Multi-account visibility = Config Aggregator
IAM policies are weaker than SCPs for governance
Tag enforcement is a cost + governance problem, not security

A buffer that automatically scales to match the throughput of data and requires no ongoing administration

Which combination of components will enable the company to create a monitoring solution that will satisfy these requirements? (Choose two.)

🧠 Trainer-Level Explanation

This is a streaming + analytics architecture question, not a database question.

AWS is testing whether you understand:

Streaming ingestion
Managed buffering
Near real-time analytics
Schema flexibility

🔑 Step 1: Understand why the current system is failing

On-prem system:

PostgreSQL database

Used as:

Event store
Ingestion buffer
Analytics backend

Why it fails:

Databases are not ingestion buffers
Heavy write volume
Storage exhaustion
Schema rigidity

AWS wants you to:

Stop using a relational database as a streaming buffer

🔑 Step 2: Decode the MOST IMPORTANT requirement

The most decisive bullet point is:

“A buffer that automatically scales to match the throughput of data and requires no ongoing administration”

This single line kills half the options.

What AWS services auto-scale with zero shard management?

❌ Kinesis Data Streams (you manage shards unless on-demand)

❌ Databases

❌ Neptune

✅ Kinesis Data Firehose

🧠 Exam rule (VERY IMPORTANT):
If the question says “no ongoing administration”, AWS prefers Firehose over Streams.

🔑 Step 3: Understand “near-real-time dashboards + JSON + dynamic schema”

This requirement screams:

Semi-structured data
Search + aggregation
Real-time dashboards

Which AWS service is built for this?

Amazon Elasticsearch Service (now Amazon OpenSearch Service)

With:

JSON documents
Dynamic schemas
Kibana dashboards
Near-real-time indexing

✅ Why Option A is Correct

Option A: Kinesis Data Firehose + Lambda

Why Firehose?

Fully managed
Auto-scales ingestion
No shard management
Built-in buffering (size + time)
Native integration with downstream analytics

Why Lambda?

Lightweight transformation
JSON enrichment
Schema normalization

This solves:

Buffering
Scaling
Operational simplicity

✅ Why Option D is Correct

Option D: Amazon Elasticsearch Service + Kibana

Why OpenSearch/Elasticsearch?

Near-real-time indexing
JSON-native
Dynamic schemas
Aggregations at scale

Kibana = dashboards out of the box

This solves:

Visualization
Analytics
Schema flexibility

🔗 How the final architecture looks (important to visualize)

On-prem → VPN → Kinesis Data Firehose
                    ↓
            Lambda (transform)
                    ↓
          Amazon OpenSearch (Elasticsearch)
                    ↓
               Kibana dashboards

This is a canonical AWS monitoring pipeline.

❌ Why the Other Options Are WRONG (Exam Traps)

❌ Option B — Kinesis Data Streams

Why this fails the requirement

Requires shard management
Requires capacity planning (unless explicitly stated on-demand)
More operational overhead than Firehose

🧠 Exam rule:
Firehose > Streams when simplicity is required.

❌ Option C — Aurora + QuickSight

Why this is wrong

Aurora is still a relational DB

Not designed for:

Streaming ingestion
Near-real-time dashboards
Schema rigidity remains

This repeats the original problem.

❌ Option E — Neptune

Why this is irrelevant

Neptune = graph database

Used for:

Relationships
Traversals

Not event ingestion
Not monitoring dashboards

Classic “sounds fancy” distractor.

🧠 Key SAP-C02 Takeaways

Streaming ingestion ≠ relational databases
Firehose = auto-scale, zero admin
Streams = more control, more ops
Near-real-time dashboards = OpenSearch
JSON + dynamic schema = document store, not RDBMS 
Question 115 – Topic 1 (Verbatim)

Question:
A team collects and routes behavioral data for an entire company. The company runs a Multi-AZ VPC environment with public subnets, private subnets, and an internet gateway. Each public subnet also contains a NAT gateway.
Most of the company’s applications read from and write to Amazon Kinesis Data Streams. Most of the workloads run in private subnets.
A solutions architect must review the infrastructure. The solutions architect needs to reduce costs and maintain the function of the applications. The solutions architect uses Cost Explorer and notices that the cost in the EC2-Other category is consistently high. A further review shows that NatGateway-Bytes charges are increasing the cost in the EC2-Other category.

What should the solutions architect do to meet these requirements?

Options (Verbatim)
✅ Correct Answer: B
🧠 Trainer-Level Explanation

This question is a classic cost-optimization + networking pattern that shows up a lot in SAP-C02.

AWS wants to know if you can:

Read a billing signal
Map it to a networking cause
Apply the correct private connectivity solution

🔑 Step 1: Understand the billing clue (VERY IMPORTANT)

The key billing phrase is:

EC2-Other → NatGateway-Bytes

This tells you:

Traffic is flowing from private subnets
Out through NAT gateways
To reach an AWS public endpoint

🧠 Exam rule:
If you see NatGateway-Bytes, the problem is almost always private subnet → AWS service over the public internet.

🔑 Step 2: Understand the traffic pattern

Given facts:

Applications are in private subnets
Applications talk to Kinesis Data Streams

Kinesis is an AWS service with a public endpoint

Without a VPC endpoint:

Traffic goes:

Private subnet → NAT Gateway → Internet → Kinesis public endpoint

You pay:

NAT hourly cost
NAT data processing cost

That explains the EC2-Other cost spike.

🔑 Step 3: What AWS expects you to do

When:

Private workloads talk heavily to AWS services
NAT costs increase
Functionality must remain the same

AWS expects you to use:

VPC endpoints

Specifically:

Interface VPC endpoints for Kinesis

✅ Why Option B is Correct (Deep Dive)

Option B says:

Add an interface VPC endpoint for Kinesis Data Streams
Ensure applications have the correct IAM permissions

This solves everything:

✅ Eliminates NAT traffic

Traffic stays inside the AWS network

No NAT gateway usage

Immediate cost reduction

✅ Maintains application behavior

Same APIs
Same SDK calls
No code changes

✅ Uses the correct security model

IAM permissions still control access
Endpoint policies are optional, not required

🧠 Important exam nuance:
For most AWS services (including Kinesis), IAM permissions are what actually authorize access, not endpoint policies.

❌ Why the Other Options Are WRONG (Important Traps)

❌ Option A — Flow Logs + Athena

Why this fails

Flow Logs help you observe

They do not:

Reduce NAT usage
Change routing

Blocking traffic would break the application

This diagnoses the problem but does not fix it.

❌ Option C — Flow Logs + Detective

Why this is wrong

Detective is for:

Security investigations
Threat analysis

This is a cost issue, not a security issue

Wrong service category.

❌ Option D — Endpoint policy focus

This is a very subtle exam trap.

Why this is not the best answer:

VPC endpoint policies are:

Optional
Default policy already allows traffic

Applications still require IAM permissions

AWS exams almost always emphasize:

IAM permissions > endpoint policies

Option D focuses on the wrong control plane.

🧠 Key SAP-C02 Takeaways

NatGateway-Bytes = private subnet → public endpoint
AWS service traffic ≠ Internet traffic (use endpoints)
Kinesis uses interface VPC endpoints
IAM permissions authorize access, not endpoint policies
Cost optimization often starts with network routing 
Question 116 – Topic 1 (Verbatim)

Question:
A retail company has an on-premises data center in Europe. The company also has a multi-Region AWS presence that includes the eu-west-1 and us-east-1 Regions.
The company wants to be able to route network traffic from its on-premises infrastructure into VPCs in either of those Regions. The company also needs to support traffic that is routed directly between VPCs in those Regions.
No single points of failure can exist on the network.

The company already has created two 1 Gbps AWS Direct Connect connections from its on-premises data center. Each connection goes into a separate Direct Connect location in Europe for high availability. These two locations are named DX-A and DX-B, respectively.
Each Region has a single AWS Transit Gateway that is configured to route all inter-VPC traffic within that Region.

Which solution will meet these requirements?

Options (Verbatim)
✅ Correct Answer: D
🧠 Trainer-Level Explanation

This is a heavy enterprise networking question.
AWS is testing whether you truly understand:

Direct Connect Gateway
Transit Gateway
Transit VIF vs Private VIF
Cross-Region routing
High availability design

This is core SAP-C02 networking.

🔑 Step 1: Restate the requirements in plain English

The company needs:

On-prem → VPCs in eu-west-1 and us-east-1
VPC ↔ VPC traffic across Regions
No single points of failure

Already has two DX connections (HA)

This is not a simple DX + VGW setup.

🔑 Step 2: Identify the ONLY VIF type that works with Transit Gateway

This is where many people fail.

Important fact (EXAM GOLD):

Transit Gateway requires a transit VIF

Private VIF works only with VGW, not TGW

So immediately:

❌ Any option using private VIF is suspicious

This alone should make you wary of Option A.

🔑 Step 3: Understand the role of Direct Connect Gateway (DXGW)

A Direct Connect Gateway:

Is global

Can connect on-prem to multiple Regions

Can associate with multiple Transit Gateways

This is exactly what we need.

🔑 Step 4: How do we enable VPC-to-VPC traffic across Regions?

Very important exam concept:

Direct Connect Gateway does NOT route traffic between Transit Gateways

DXGW only routes:

On-prem ↔ TGW

To allow:

eu-west-1 VPC ↔ us-east-1 VPC

You must:

Peer the Transit Gateways

🧠 Exam rule:
Cross-Region VPC traffic always requires Transit Gateway peering.

✅ Why Option D is Correct (Deep Dive)

Option D does all the right things:

✅ Uses transit VIFs (correct)

Required for Transit Gateway

✅ Uses a single DXGW with two DX connections

DX-A + DX-B → high availability

No single point of failure

✅ Associates both regional Transit Gateways

On-prem can reach both Regions

✅ Peers the Transit Gateways

Enables cross-Region VPC routing

This design:

Is AWS reference architecture
Meets all requirements
Is highly available
Scales cleanly

❌ Why the Other Options Are WRONG (Critical Exam Traps)

❌ Option A — Private VIF (Fatal mistake)

Why this fails

Private VIF cannot attach to Transit Gateway

Private VIF works with VGW only

🧠 EXAM GOLD:
If TGW is involved → you need transit VIF, not private VIF.

❌ Option B — Multiple DX Gateways

Why this is wrong

Direct Connect Gateways are:

Global

Highly available

Creating multiple DXGWs:

Adds complexity
Provides no real benefit

DXGWs cannot be peered

This option invents unnecessary architecture.

❌ Option C — DXGW routing between TGWs

Why this fails

DXGW cannot route traffic between Transit Gateways

Only TGW peering enables cross-Region routing

This is a very subtle but common exam trap.

🧠 Key SAP-C02 Takeaways

Transit Gateway requires transit VIF
Private VIF ≠ Transit Gateway
Direct Connect Gateway is global
DXGW does NOT route between TGWs
Cross-Region VPC traffic = TGW peering

This is a “keyword soup” distractor.

❌ Option F — IAM users + Cognito

Why this is wrong:

IAM users do not scale

Cognito is for application users, not AWS admins

AWS strongly discourages IAM users in large orgs

Enterprise access = federation + SSO, not IAM users.

Question 120 – Topic 1 (Verbatim)

Question:
A company is building a software-as-a-service (SaaS) solution on AWS. The company has deployed an Amazon API Gateway REST API with AWS Lambda integration in multiple AWS Regions and in the same production account.
The company offers tiered pricing that gives customers the ability to pay for the capacity to make a certain number of API calls per second. The premium tier offers up to 3,000 calls per second, and customers are identified by a unique API key.
Several premium tier customers in various Regions report that they receive error responses of 429 Too Many Requests from multiple API methods during peak usage hours. Logs indicate that the Lambda function is never invoked.

What could be the cause of the error messages for these customers?

Options (Verbatim)
✅ Correct Answer: C
🧠 Trainer-Level Explanation

This question is all about where throttling occurs and who is doing the throttling.

AWS is testing whether you understand:

API Gateway throttling layers
Account-level vs method-level limits
The difference between API Gateway throttling and Lambda throttling

🔑 Step 1: Lock onto the most important clue

The single most important sentence in the question is:

“Logs indicate that the Lambda function is never invoked.”

This immediately tells us:

❌ Lambda is NOT the source of throttling

❌ Lambda concurrency limits are irrelevant

✅ Throttling is happening before Lambda

🧠 EXAM GOLD:
If Lambda is never invoked → the problem is upstream.

🔑 Step 2: Identify where throttling can occur BEFORE Lambda

Before a request reaches Lambda, it passes through:

API Gateway

Usage plans (API keys)

Throttling limits

API Gateway enforces throttling at:

Account level

Stage level

Method level

Usage plan level

🔑 Step 3: Understand API Gateway limits (very important)

Key API Gateway limits (REST API):

Account-level limit:

~10,000 requests per second per Region (default)

Per-method default limit:

~1,000 requests per second

Usage plan limits:

Rate + burst, per API key

🔑 Step 4: Why the account-level limit is the real culprit

Important clues:

Multiple API methods are affected

Multiple Regions

Premium customers (high throughput)

Same production account

This tells us:

Traffic from many customers

Summed across methods

Summed across APIs

All within the same account

That points to:

API Gateway account-level throttling

✅ Why Option C is Correct (Deep Dive)

Option C says:

The company reached its API Gateway account limit for calls per second

This perfectly matches the symptoms:

Throttling occurs before Lambda

Affects multiple methods

Happens during peak usage

Customers see 429 errors

API Gateway blocks the request and never forwards it to Lambda → exactly what the logs show.

❌ Why the Other Options Are WRONG (Critical Exam Traps)

❌ Option A — Lambda concurrency limit

Why this fails:

If Lambda concurrency were exceeded:

Lambda would still be invoked

Logs would show invocation attempts

The question explicitly says Lambda is never invoked

Immediate elimination.

❌ Option B — Lambda Regional concurrency limit

Same reasoning as Option A:

Lambda must be invoked for concurrency limits to apply

Throttling here would be after API Gateway

Wrong layer.

❌ Option D — Per-method API Gateway limit

Why this is tempting but wrong:

Per-method limit affects one method

The question says:

“multiple API methods”

🧠 EXAM RULE:
If multiple methods are failing → it’s not a per-method limit.

🧠 Key SAP-C02 Takeaways

429 before Lambda = API Gateway throttling
Lambda concurrency ≠ API Gateway throttling
Multiple methods failing = account-level limit
API Gateway blocks requests before Lambda

Always locate where the failure occurs in the request path
